# 自动化与触发器

一条自动化 = **什么时候跑** + **跑什么**。

跑什么由自动化自己描述：工作区、提示词、模型、权限。什么时候跑由触发器描述：
一个事件源加一个条件。两者存在同一条记录里（`~/.pocketagent/automations.json`），
所以列表里看到的就是一条完整的规则，不用在「计划」和「触发器」两个页面之间来回对。

```
事件源（四种） ──→ Occurrence ──→ 匹配 → 去重 → 环路/频次 → 并发 → 条件 ──→ 开任务
```

## 四种事件源

| 源 | 什么时候产生 | 去重键 | 典型用途 |
|---|---|---|---|
| `clock` | 到点（每天几点 / 每隔 N 分钟） | `clock:<id>:<计划时间>` | 每日巡检、每小时跑测试 |
| `task_end` | 某个任务的一轮跑完 | `task_end:<会话>:<第几轮>` | a 做完接着做 b |
| `webhook` | 外面 POST 过来 | `X-PocketAgent-Delivery`，没有就用正文指纹 | CI 变绿、表单提交、别的系统推消息 |
| `poll` | 每隔 N 分钟跑一条命令，退出码 0 | `poll:<id>:<分钟>` | 盯一个只有轮询才拿得到的状态 |

`task_end` 可以指定等哪条自动化（`automation_id`），留空表示任何自动化跑完都算。
手动开的任务也会发这个事件，它的 `automation_id` 是空的。

两种源都只看「这一轮结束了」，不看是谁按的按钮；区别只在过滤条件。

### 轮询脚本拿到什么

stdin 是一份 JSON：

```json
{"event": "poll", "automation_id": "a1b2", "automation_name": "盯 CI", "workspace": "/Users/me/repo", "at": "2026-10-30T15:00:00"}
```

退出码 0 = 现在该跑了；1 = 还没有（不算出错）；其他值 = 脚本自己坏了，界面上的「问题」会显示原因。
单飞：上一次没跑完不会叠加；超过 `timeout_seconds`（默认 30 秒，上限 600）连子进程一起结束。

## 条件

条件是「这次算不算数」，四种：

| 条件 | 判断依据 | 说明 |
|---|---|---|
| `always` | 恒真 | 默认 |
| `status` | `stop_reason` 等于指定值（默认 `done`） | 只在 `task_end` 上有意义：上游失败就别往下传 |
| `match` | 最后一段话匹配正则 | 比如要求上游结尾写 `[[DONE]]` |
| `shell` | 命令退出码 0 | 最灵活，也最贵 |

`shell` 的退出码约定：**0 算数，1 明确说不，其他值和超时算脚本出了问题**（不触发，并在列表里标出来）。
注意这跟钩子不一样——钩子里退出码 2 是「拦住」，触发器里没有这个概念，别把两套记混。

## 判定顺序

引擎对每一次 `Occurrence` 按这个顺序判，前四步都是纯内存，第五步才可能 fork 进程：

1. **匹配**：这条自动化配的是不是这个源
2. **去重**：同一个键在 24 小时内只算一次（webhook 重试、连点、连着重启都挡在这里）
3. **频次和环路**：一小时最多 12 次；触发链最多 3 层
4. **并发**：上一次还在跑就跳过，不排队
5. **条件**：正则 / 状态 / 脚本

跳过不等于静默：引擎会返回一条 `FireOutcome`，里面写着原因（「已经处理过」「上一次还在跑」……）。
`tick()` 和 `fire()` 都返回它，测试就是靠这个断言「应该不跑」。

**宁可少跑一次，也不少跑两次。** 记账在跑之前，进程中途崩了不会重放。

## 环路怎么断

a 跑完触发 b，b 跑完又触发 a，这种配置是合法的也是危险的。两道闸：

- 深度：a 拉起的任务深度是 1，b 是 2，到 3 就不再往下传
- 频次：同一条自动化一小时内最多 12 次

两个都要有——深度挡长链，频次挡一堆兄弟节点同时触发。

## 外部 POST

每条 `webhook` 自动化有自己的密钥（保存时生成，编辑别的字段不会换）。地址：

```
POST http://127.0.0.1:8765/api/triggers/<自动化 id>/hook
X-PocketAgent-Signature: sha256=<HMAC-SHA256(正文, 密钥)>
X-PocketAgent-Delivery: <每次调用一个唯一 id>
```

```bash
BODY='{"build": 42}'
SIG=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)
curl -sS -X POST "http://127.0.0.1:8765/api/triggers/$AUTOMATION_ID/hook" \
  -H "X-PocketAgent-Signature: sha256=$SIG" \
  -H "X-PocketAgent-Delivery: build-42-1" \
  -d "$BODY"
```

返回 `{"fired": true, "reason": "已启动", "session_id": "..."}`；重复的 delivery id 会返回
`{"fired": false, "reason": "这件事已经处理过"}`，并且返回 200——重试是正常现象，不该让调用方以为失败了。

这一条路由**不走主 token**：签名用的密钥在每条自动化上，外面的系统不该拿到能控制整个服务的 token。
中间件只对这一个路径放行，验签在 `routes/automations.py` 里，是唯一的门。

## 老格式

以前的 `automations.json` 把计划平铺在记录上（`schedule_kind` / `daily_time` / `weekdays` /
`interval_minutes`）。读进来会转成 `clock` 源，存回去只写 `trigger` 一个字段，不需要手动迁移：

```json
{
  "id": "a1b2",
  "name": "每日巡检",
  "trigger": {
    "source": {"kind": "clock", "mode": "daily", "daily_time": "09:00", "weekdays": [0, 1, 2, 3, 4]},
    "condition": {"kind": "always"}
  }
}
```

## 和钩子怎么分工

两件事看起来像，其实不是：

| | 钩子 | 触发器 |
|---|---|---|
| 位置 | 一轮内部，跟着 agent 走 | 一轮之外，跟任务无关 |
| 能做什么 | 拦住这次调用、给模型补上下文、拦下这一轮 | 只能开一个新任务 |
| 配在哪 | `config.json`，对所有会话生效 | `automations.json`，一条对一条 |
| 典型用途 | 提交前跑 lint、危险命令拦一下 | a 做完跑 b、8 点跑 c、CI 绿了跑 d |

分界线是「要不要影响正在跑的这一轮」。要影响就用钩子，只是「发生了就再开一局」就用触发器。
CLI 里跑完的任务不会发触发事件（没有服务在听），那种情况让 CLI 的 `turn_end` 钩子去 POST webhook。

## 已知边界

- **只有 web 服务（或桌面端的后端）开着才跑。** 命令行、TUI 关掉之后没有东西在听事件。
- **错过的事件补不回来。** `clock` 错过的计划下次启动补跑一次；`task_end` / `webhook` / `poll`
  在进程不在的时候发生就是错过了。假装能补，代价是任务被重放一遍。
- **轮询计时器在内存里。** 重启后重新计时，不会因为重启立刻多跑一次。
- **触发器只表达一条边。** a→b→c 就配两条记录。别往这里加 `depends_on`，那是工作流引擎的活儿。
